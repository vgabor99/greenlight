# Firmware

ESP-IDF v6.1, C, CMake. Coding conventions (prefixes, includes, log tags) are in [CLAUDE.md](../CLAUDE.md).

## Source layout

Every file under `main/` has one purpose and is named after it. The files are grouped by concern, and a concern
knows only the ones below it, so a different panel or a different screen design changes only its own part:

| Concern | Where | Knows nothing of |
|---|---|---|
| The data HA and the device share ([data-model.md](data-model.md)): dataset, view, line format, and the rule for what a view means | `data_model.c` | Zigbee, the screens, the panel |
| The application state, and from it alone what should be on the screen: which screen, the shown lines, stale or not; no sizes, texts or icons. Applies and acknowledges what HA sends | `app/` | the screens, the panel |
| The UI: lays the screen out and draws it into a framebuffer of the panel's size | `screen/` | the state machine, Zigbee, the panel driver |
| The output device: the panel driver and its refresh policy | `panel/` | what a frame shows |
| Keeping the panel showing the state: snapshot, draw, send, and when to redraw | `display/` | how a screen looks |
| The transport to HA: decodes HA's writes into views, dataset entries and commits, sends the reports it is asked to | `zigbee/` | what the data means: the application state, the rules, the screens |
| Behaviour: states, timeouts, reports, sleep | `state_machine.c` | how the screens look, the panel |
| The board and storage: pins, inputs, battery, sleep, NVS | `board/`, `persistent_store.c` | the application |
| Diagnostics | `console.c`, the debug screen, `SCREEN_DUMP` | |

Dependencies point down: `state_machine.c` -> `display/` -> `screen/` -> `panel/` -> `board/`. The state machine,
`display/` and `screen/` read `app/`. `app/` in turn uses `data_model.c`, `persistent_store.c` and the battery, and
`zigbee/` to acknowledge what HA sent. `zigbee/` calls back into `app/ha_input.c` only through the callbacks the
state machine hands it. So another 1-bit panel changes `panel/` (the size follows), the layout constants in
`screen/status_screen.c` and the bitmaps; another screen design changes `screen/status_screen.c`.

| Path | Purpose |
|---|---|
| `main.c` | start-up order: sets up the parts, then runs the state machine |
| `state_machine.c` | the states and timeouts ([behaviour.md](behaviour.md)) |
| `console.c` | USB console commands (`bat`, `usb`, `vbat`) |
| `persistent_store.c` | NVS keys and access ([Persistent state](#persistent-state)) |
| `data_model.c` | dataset, view and line types and limits, the line format parser, what a view means |
| `board/board.c` | pin map (`board.h`), RF switch |
| `board/inputs.c` | PIR and pair button: polling, debounce, occupancy hold |
| `board/battery.c` | battery voltage and USB power (measured, or the console's overrides), low-battery latch |
| `board/battery_sense.c` | battery measurement on D2 (ADC) |
| `board/usb_sense.c` | USB sense on GPIO7 (the MTDO pad) |
| `board/sleep.c` | deep sleep (or the simulated sleep) |
| `board/wake_reason.c` | the wake cause, logged at boot |
| `app/app_state.c` | the mutex-guarded application state (device state, wake failure, dataset, shown view, received writes), its snapshot |
| `app/ha_input.c` | HA's views and datasets: checked against the state, applied, acknowledged ([zigbee.md](zigbee.md#input-ha-to-device)) |
| `app/keep_awake.c` | how long the wake must go on besides the inputs: a deadline that HA's writes and the states extend ([behaviour.md](behaviour.md#timeouts)) |
| `app/screen_content.c` | what should be on the screen for a state (`screen_content_of()`) |
| `app/device_state.c` | the device states and wake failures |
| `app/view_freshness.c` | staleness deadline in RTC memory ([data-model.md](data-model.md#staleness-flag)) |
| `display/display.c` | panel power on and off, redraw, `display_wait_ms()` |
| `screen/render.c` | picks the proper or the debug screen; whether a redraw would change the screen |
| `screen/status_screen.c` | the proper screen, with its row layout ([display.md](display.md)) |
| `screen/debug_screen.c` | the RnD debug screen |
| `screen/bitmap_text.c` | Inter text and icons from the bitmaps |
| `screen/bitmaps.c` | generated by `tools/gen_bitmaps.py`, never edited by hand |
| `screen/framebuffer.c` | the 1-bit framebuffer, the panel's size (also u8g2's draw target) |
| `screen/sample_screens.c` | `SCREEN_DUMP`: every screen once with sample content |
| `panel/panel.c` | refresh / clear policy, the frame kept through sleep, power on and off, and the `panel:` log |
| `panel/epaper.c` | SSD1683 driver ([hardware.md](hardware.md#e-paper-panel)) |
| `panel/frame_dump.c` | `SCREEN_DUMP` output of a frame |
| `zigbee/zigbee.c` | stack, network, public API |
| `zigbee/zigbee_device.c` | endpoint and clusters ([zigbee.md](zigbee.md#endpoint-and-clusters)) |
| `zigbee/zigbee_display_input.c` | decodes the view and dataset writes, reassembles the dataset ([zigbee.md](zigbee.md#input-ha-to-device)) |
| `zigbee/zigbee_reports.c` | reports to the coordinator and their confirmations ([zigbee.md](zigbee.md#state-device-to-ha)) |
| `zigbee/zigbee_internal.h` | shared between the `zigbee/` files only |
| `util/utf8.c`, `util/hex.h`, `util/elapsed_time.h` | helpers |

Other folders: `tools/` (bitmap and mockup generators, serial console, framebuffer dump, Zigbee bench test,
docs checker), `z2m/` (the Zigbee2MQTT converter), `ha/` (the Home Assistant sources).

External dependencies: the Zigbee libraries (`espressif__esp-zigbee-lib`, `esp-zboss-lib`) and u8g2 (upstream
git, pinned to a commit), all in `main/idf_component.yml`. u8g2 is used only for the debug screen's font and text,
drawn through a callback into the framebuffer, never for the panel. The top-level `CMakeLists.txt` sets
`MINIMAL_BUILD ON`, so a new component dependency must be declared in `main/CMakeLists.txt` (`PRIV_REQUIRES`).

`sdkconfig` is generated and git-ignored; `sdkconfig.defaults` (from `idf.py save-defconfig`: target,
USB-Serial-JTAG primary console, Zigbee end device) holds the non-default settings, so rerun `save-defconfig`
after changing `menuconfig`. `sdkconfig.ci` holds CI-only overrides (currently empty). `.clangd` strips `-f*` / `-m*` flags so clangd copes with the RISC-V GCC flags in
`compile_commands.json`.

## Tasks and data flow

- `app_main()` sets up the parts in order, then runs the state machine (`state_machine_run()`) in the main task.
- `input_task` polls and debounces D0 and D1 (level based); `console_task` reads the console commands.
- The Zigbee task runs the stack and decodes HA's writes; a view is handed on by `deliver_view()` after the whole
  frame has been processed. In the same task `app/ha_input.c` checks each against the mutex-guarded application
  state (`app/app_state.c`, which counts its changes), applies it and sends the acknowledgement.
- The state loops wait with `display_wait_ms()`. It takes a snapshot of the state and redraws when the screen would
  change (`render_is_outdated()`): the proper screen when what should be on it changes (the staleness flag
  included), the debug screen on any change of the state, the shown age or the battery simulation. So a burst of
  writes is drawn as it arrives; writes during a refresh (about 0.5 s) coalesce into the next one.

## Persistent state

A wake is a reset, so what must survive sleep is in NVS, namespace `greenlight` (`persistent_store.h`; the key
strings address state on devices, never change them). The Zigbee stack keeps the network in the same partition.

| Key | Content |
|---|---|
| `pair_now` | start pairing right after the next boot (set by ERASE_NETWORK) |
| `wake_n` | the wake counter |
| `ds` | the dataset |
| `view` | the shown view with the text of its active lines |
| `sim_mv`, `sim_usb` | the console's overrides: battery voltage (0 = measured), USB power (0 = sensed, 1 = USB, 2 = battery) |
| `bat_low` | the low-battery latch |

The staleness deadline lives in RTC memory (`RTC_NOINIT_ATTR`): it survives a restart and deep sleep, and is
cleared after a power-on. The frame on the panel lives there too (15,000 of the 16,360 bytes of LP RAM), with a
magic value and a CRC that `panel_power_off()` sets only when the panel shows that frame
([behaviour.md](behaviour.md#panel-on-each-wake)).

To get a factory-new device, erase NVS: `python -m esptool --chip esp32c6 -p COM5 erase-region 0x9000 0x6000`.

## Build switches

CMake caches them; pass `=0` to switch back.

| Switch | Effect |
|---|---|
| `-DDEBUG_SCREEN=1` | the RnD debug screen instead of the proper screen ([display.md](display.md#debug-screen)) |
| `-DSCREEN_DUMP=1` | print every frame on the console for `tools/fb_dump.py` ([display.md](display.md#checking-against-the-mockups)) |
| `-DSLEEP_TIMER_S=N` | a timer also ends deep sleep after N s (bench tests) |
| `-DSIM_SLEEP=1` | simulated sleep: wait for D0 or D1, then `esp_restart()`. USB, the log, the console and resets over USB keep working, so use it for autonomous testing. |

## Battery and USB power

- **The battery voltage** is measured on D2 at boot, before the radio and the panel start (logged as `battery
  sense: pin ... mV, vbat ... mV`), and again, unlogged, at every mid-wake battery check
  ([behaviour.md](behaviour.md#low-battery)). The `vbat` console command measures and logs.
- **USB power** is read from GPIO7 (the MTDO pad, `usb_sense_read()`). With USB in, a low battery never counts
  (USB power overrides it), and the serial log only works with USB in: so bench tests of the low battery use the
  overrides.
- **The overrides** are set over the USB-Serial-JTAG console (the primary console, so it takes input): `bat <mV>`
  (2500-4500; `bat 0` = measured again), `usb 0|1` (battery / USB; `usb auto` = sensed again); `bat` / `usb`
  alone print them, as `battery: 3864 mV (measured), usb 1 (sensed; sense 1), latched 0`. They are kept in NVS
  (`sim_mv`, `sim_usb`; default measured and sensed), so they survive the sleep, a power cycle and a reflash:
  clear them after a test. Usage with `tools/console.py`: the `bench-test` skill.
- **LOW_BATTERY** deep-sleeps with GPIO7 going high as its only wake (`sleep_until_usb_power()`). If USB is
  already on the pin there (`usb 0` with the cable in), a sleep would end at once, so it waits awake for the
  console (`usb 1` or `usb auto`) and then restarts.
